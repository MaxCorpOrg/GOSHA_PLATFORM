# GPT-Live-1 и GPT-5.5 в голосовом контуре Гоши

Состояние 13 сентября 2026: программный кандидат в ветке
`codex/gpt-live-1-voice-20260913`, основанной на серверном кандидате `1c9cfc9`.
SSH-доступ восстановлен после сверки текущего IP сервера в Hostkey.
На сервере подготовлен отдельный процесс из кода `7f54630`, health и
18 тестов прошли. Публичный маршрут и основной app пока используют прежний
голосовой движок. `OPENAI_API_KEY` на сервере отсутствует, баланс API — $0.
Реальное соединение с OpenAI, слышимый ответ, русский голос и задержка
ещё не приняты.

## Архитектура

До переключения используется существующая цепочка Vosk → DeepSeek → Silero
с резервом EdgeTTS. Новый отдельный процесс `gosha-voice-router.service`
принимает тот же WebSocket робота и выбирает путь по профилю ассистента:

```
Робот: Opus, 16000 Гц, моно, 60 мс
   → проверка Device-Id и Bearer по действующей привязке
   → профиль ассистента.voice_engine
       chained     → существующий совместимый сервер без преобразования кадров
       openai_live → libopus decode → PCM16LE 16000 Гц → GPT-Live-1
                                                            ↕
                                                     Responses GPT-5.5
                    робот ← libopus encode ← PCM16LE ← голосовой ответ
```

Для Live используется `wss://api.openai.com/v1/live/sessions`, первый кадр
`session.start`. Модель речи — `gpt-live-1`; модель рассуждений задаётся отдельно
в `delegation.responses.model` как `gpt-5.5`. Это не подстановка модели в старый
Realtime API и не новый TTS-плагин. Голос по умолчанию `marin`, глубина
рассуждений `medium`; её можно выбирать отдельно (`low/medium/high/xhigh`).

Поля профиля ассистента:

| Поле | Значение для нового контура |
|---|---|
| `voice_engine` | `openai_live`; прежнее значение по умолчанию — `chained` |
| `live_voice` | `marin` или другой перечисленный в панели голос GPT-Live |
| `live_reasoning_effort` | `medium` |
| `provider_profile_id` | профиль OpenAI, `https://api.openai.com/v1`, модель `gpt-5.5` |
| `model_override` | пусто либо `gpt-5.5` |

Поля сохраняются через существующий `/api/operator/assistant-profiles`.
Они доступны в общем редакторе профиля и на странице выбранного робота.
Сохранение профиля Live и смена привязки в/из Live не перезапускают прежний
голосовой сервер: API возвращает `activation:next_voice_connection` и
`runtime_verified:false`.
Ответ эффективной конфигурации содержит `voice_runtime`: это сведения о выборе,
а не доказательство соединения с API. Старые `voice_profile` и `tts_engine_profile`
сохраняются для возврата к прежнему пути. Они не задают голос GPT-Live.

Ключ читается только процессом сервера из `OPENAI_API_KEY`, заданного в защищённом
`providers.env`. В профилях хранится имя переменной. Ключ не передаётся в браузер,
роботу или резервному голосовому серверу.

## Что проверено программно

- Преобразование PCM/Opus настоящей системной `libopus`, заголовки протоколов 1/2/3.
- Точные поля Live API, раздельные модели речи и рассуждений, отсутствие аппаратных tools.
- Локальный WebSocket: начало/конец речи, аудио в обоих направлениях и равномерная отправка.
- Очистка старого входящего/исходящего звука при явном `abort`, новая Live-сессия.
- Длинный ответ создаёт обратное давление на очередь вместо аварийного переполнения.
- Закрытие неактивного сеанса, `session.close` и получение финальной статистики.
- Проверка ключа устройства до обращения к платному API, сохранение полей профиля и резервной копии привязки.
- Общие проверки платформы, включая события, onboarding и прежний аудиоконтракт.

Проверка `ops/probe_gpt_live.py` честно возвращает `openai_api_key_missing` в
текущем окружении. Имитаторы не подтверждают доступ аккаунта к моделям.

## Выполненная подготовка на действующем сервере

Сохранённый SSH-адрес устарел. API Hostkey подтвердил ту же услугу VPS,
активную аренду, другой IP и срок оплаты до 22 сентября. Вход выполнен
существующим SSH-ключом с проверкой прежнего host key. Рабочие адреса
и сведения доступа сохранены только в локальных свидетельствах задачи.

Действующая схема проверена по серверной конфигурации:

```
Робот → внешний relay → основной сервер
                         ├─ :18876 панель, mobile API и OTA
                         └─ :18080 голосовой контейнер
                              VoskASR → внутренний OpenAI-совместимый
                              прокси панели → deepseek-v4-flash → Silero kseniya
```

Панель и внешний relay вернули HTTP 200. Все три основные службы active.
В каталоге основного app нет git; отдельные файлы отличаются от базы
кандидата. Не заменять этот каталог целиком: сначала сохранить и совместить
серверные правки с изменениями GPT-Live.

В `/opt/gosha_platform/runtime/staging/gpt-live-7f54630` помещён отдельный
архив проверенного кода. В `/opt/gosha_platform/voice-venv` установлена
`websockets 15.0.1`; системная libopus доступна. Все 18 тестов прошли на
самом сервере с временными тестовыми данными, без OpenAI и робота.

Временная служба `gosha-voice-router-stage.service` запущена через
`systemd-run` с ограничениями из репозиторного unit-файла, отдельным путём
к исходникам и bind `127.0.0.1:18084`. Она читает существующий APP_ROOT,
а прежний голосовой путь направляет на `127.0.0.1:18080`. Проверка
`http://127.0.0.1:18084/healthz` — HTTP 200. Служба временная: после
перезагрузки сервера её нужно запускать снова либо выполнить окончательную
установку из совмещённого app.

Для остановки только подготовительного процесса:

```bash
systemctl stop gosha-voice-router-stage.service
```

На публичном `18080` остаётся прежний контейнер. Основные службы не
перезапускались; профили, relay, настройки робота и прошивка не менялись.
Полная установка ниже остаётся следующим этапом после ключа, оплаты API,
реальной API-проверки и совмещения серверного кода.

## Подготовка сервера

Требуются Python 3.11+, системная `libopus0`, `python3-venv`, зависимость
`websockets>=11,<16` и исходники этой ветки. Размещать изменения в серверном
`app` следует после сверки установленного кода: нельзя переписать более новые
или несвязанные серверные изменения старым checkout целиком.

В защищённом `/opt/gosha_platform/runtime/env/providers.env` должен существовать
`OPENAI_API_KEY`. Значение не передавать аргументом команды и не выводить.

Подготовительный запуск сохраняет текущий публичный маршрут:

```bash
cd /opt/gosha_platform/app
bash ops/install_server.sh --voice-router-stage
curl --fail http://127.0.0.1:18084/healthz
```

Он устанавливает отдельную среду `voice-venv`, unit и конфигурацию
`runtime/env/voice-router.env`. Сам по себе `healthz` подтверждает только
готовность процесса. Чтобы панель отображала новые поля, её серверный код и
HTML тоже должны быть обновлены этой проверенной правкой.

Подготовить профиль и проверить доступ к API:

```bash
APP_ROOT=/opt/gosha_platform/runtime/app_root \
  /opt/gosha_platform/voice-venv/bin/python ops/configure_gpt_live.py \
  --robot-id ROBOT_ID \
  --providers-env /opt/gosha_platform/runtime/env/providers.env

APP_ROOT=/opt/gosha_platform/runtime/app_root \
  /opt/gosha_platform/voice-venv/bin/python ops/configure_gpt_live.py \
  --robot-id ROBOT_ID \
  --providers-env /opt/gosha_platform/runtime/env/providers.env --probe
```

Заменить `ROBOT_ID` действующей серверной личностью робота.
`--probe` — короткий платный запрос без обращения к устройству. Он проверяет
обе модели, `session.started`, отдельный запрос приветствия с подтверждением
инструкции, ответ GPT-5.5 на контрольный расчёт, поступление
ненулевого голосового PCM и `session.closed`. Аудио нигде не сохраняется.
Результат не доказывает воспроизведение на динамике или точность произношения.

После успешной проверки `--apply` повторяет её, создаёт отдельные профили
`live-gpt55-ROBOT_ID` и `live-assistant-ROBOT_ID`, затем меняет только выбранный
профиль ассистента в привязке этого робота. Прежние поля привязки, стандартные
профили и другие роботы сохраняются. До записи создаётся закрытая резервная
копия трёх файлов в `APP_ROOT/voice_live_backups/<id>/` с манифестом.
Ошибки записи откатываются к исходным файлам.

## Подключение публичного маршрута и возврат

Эта процедура **не выполнялась**. После проверки действующих портов и
завершения текущего голосового разговора:

1. Сохранить закрытые копии `selfhost-backend.env` и `voice-router.env`,
   действующие привязки и сведения о запущенных службах.
2. Перенести только порт совместимого голосового контейнера на
   `SELFHOST_XIAOZHI_WS_BIND=127.0.0.1`, `SELFHOST_XIAOZHI_WS_PORT=18081`.
   Применить `docker compose ... up -d --no-deps xiaozhi-esp32-server`
   с существующими project/env/compose параметрами. Не останавливать БД и Redis.
3. В `voice-router.env` задать `GOSHA_VOICE_HOST=0.0.0.0`,
   `GOSHA_VOICE_PORT=18080`, `GOSHA_VOICE_LEGACY_URL=ws://127.0.0.1:18081`.
   Перезапустить только `gosha-voice-router.service`.
4. Проверить локальные health, старый голосовой путь для `chained`, отсутствие
   доступа Live с неверным токеном, затем свежий разговор выбранного робота.
   Внешний URL робота, OTA, relay, прошивка и NVS при этом не меняются.
5. При ошибке остановить router, восстановить оба сохранённых env-файла и
   пересоздать только голосовой контейнер с прежним портом. Для отмены
   назначения ассистента восстановить исходные файлы по манифесту резервной
   копии профилей. Не возвращать `chained` в новый GPT-5.5 профиль как замену
   полноценного восстановления прежнего ассистента.

## Ограничения до аппаратной приёмки

- В обычном режиме прошивка выключает микрофон в состоянии Speaking.
  Сервер дополняет отсутствующий поток тишиной и подавляет короткие
  пересекающиеся голосовые подтверждения. Перебивание здесь возможно только
  явным `abort` от прошивки, например при новом слове пробуждения. После abort
  прежняя API-сессия закрывается, а новая получает только ограниченный текстовый
  контекст пользовательских реплик в памяти и новую речь. Сгенерированный
  текст ассистента не считается услышанным и не переносится в новый сеанс. При пяти последовательных перезапусках
  соединение завершается.
- `listen mode=realtime` позволяет передавать микрофон во время ответа,
  но качество эхоподавления и свободного перебивания на устройстве не проверено.
  Этот режим не включается автоматически и не требует новой прошивки в текущей
  программной задаче.
- Live не имеет события окончания выходящего аудио. Router использует очередь
  и 720 мс тишины для `tts:stop`, а перед первым звуком даёт прошивке время и
  тихий кадр для перехода в Speaking. Это совместимый способ доставки,
  а не подтверждение физического воспроизведения. Тихая речь, длинные паузы,
  фоновые звуки и сетевые задержки требуют проверки на роботе.
- Сеанс ограничен 300 секундами и 60 секундами неактивности, одновременно
  допускается до четырёх Live-разговоров и один на личность робота.
  Закрытие ждёт `session.closed` до 15 секунд; при потере сети финальная
  статистика помечается неподтверждённой. Голос оплачивается по времени,
  GPT-5.5 — отдельно.
- Инструменты MCP, движение, OTA, память прежнего ASR/LLM/TTS-контейнера и
  его база знаний в Live не подключены. Передаются роль и системные инструкции
  текущего ассистента, а краткая история хранится только до закрытия соединения.
  Аппаратные команды не генерируются и не выполняются.
