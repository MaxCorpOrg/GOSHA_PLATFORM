# План собственного контура операторских команд «Гоша»

Дата фиксации: `2026-07-23`.

## Цель

Перевести операторские команды со старого облачного моста на собственный масштабируемый контур платформы `Гоша`:

```text
панель оператора
    ↓
операторский API платформы
    ↓
диспетчер и хранилище команд
    ↓
собственный шлюз соединений с роботами
    ↓
конкретный робот
    ↓
подтверждающие события и результат
    ↓
общий runtime-контур → панель и разрешённые мобильные клиенты
```

Первый обязательный набор:

- получить подтверждённый статус робота;
- получить заряд батареи;
- выполнить аварийную остановку;
- выполнить одно безопасное действие без движения;
- показать оператору весь путь команды от постановки до результата.

Архитектура сразу рассчитывается на много роботов, операторов, панелей и параллельных команд. `gosha_agent_gateway.py`, который маршрутизирует запросы к поставщикам ИИ, остаётся отдельной службой и не смешивается со шлюзом команд физических роботов.

## Исходное состояние

Уже готово:

- общий контракт наблюдаемости `gosha.runtime.event.v1`;
- события робота, Android-клиента и панели;
- агрегация связей, задач, ошибок и статистики;
- операторский поток событий в реальном времени;
- существующий режим `edge-hub` и диагностика его транспорта;
- живой OTA- и голосовой контур;
- подтверждённый сценарий восстановления Android после потери Wi-Fi.

Не готово:

- собственная достоверная доставка операторской команды до физического робота;
- подтверждение принятия и результата команды самим роботом;
- регистрация текущего боевого робота в собственном шлюзе управления;
- отказ от старого облачного моста как основного маршрута `status`, `battery`, `stop` и действий.

## Базовые архитектурные решения

### 1. Отдельный контракт команд

Нужен версионированный конверт `gosha.robot.command.v1`. Минимальные поля:

- `command_id` — глобально уникальный идентификатор;
- `robot_id` — берётся сервером из проверенного маршрута, а не из произвольного тела;
- `kind` — разрешённый вид команды;
- `arguments` — проверенная структура параметров конкретной команды;
- `created_at` и `expires_at`;
- `idempotency_key` — защита от повторного выполнения;
- `priority` — обычная или аварийная;
- `trace.correlation_id` и `trace.causation_id`;
- сведения об операторе, выведенные из серверной сессии.

Произвольный вызов любого метода `MCP` из браузера запрещён. Публичный операторский API принимает только явный список разрешённых команд.

### 2. Единый жизненный цикл

Команда и её runtime-задача используют один `command_id` и один `correlation_id`.

| Шаг | Состояние задачи | Что является доказательством |
|---|---|---|
| Команда принята платформой | `queued` | запись создана атомарно |
| Команда передана в активную сессию робота | `running` | шлюз записал доставку |
| Робот подтвердил принятие | `running` | подтверждение от авторизованной сессии робота |
| Робот завершил действие | `completed` | результат с тем же `command_id` |
| Робот отклонил или не выполнил действие | `failed` | безопасный код ошибки |
| Истёк срок ожидания | `timed_out` | серверный таймер, повторного скрытого выполнения нет |
| Оператор отменил ещё не начатую команду | `cancelled` | атомарный переход до принятия роботом |

Состояние не выводится только из наличия WebSocket-соединения. Статус «выполнено» возможен лишь после ответа физического робота.

### 3. Соединение робота

- Робот сам открывает исходящее защищённое соединение с платформой, поэтому не требуется входящий адрес робота в домашней сети.
- Устройство проходит проверку собственным ключом и получает только свою очередь.
- Каждая новая сессия получает `instance_id` и номер поколения. Старая сессия после переподключения не может подтверждать новые команды.
- При повторной доставке робот обязан распознавать уже обработанный `idempotency_key`.
- Робот сообщает версию протокола и поддерживаемые возможности: статус, батарея, остановка и доступные безопасные действия.
- Очередь ограничена по размеру и времени жизни. Просроченная команда никогда не исполняется после позднего переподключения.

### 4. Безопасность

- Проверка прав выполняется на уровне оператора, робота и вида команды.
- Команды движения по умолчанию запрещены до отдельной приёмки безопасности.
- Аварийная остановка имеет повышенный приоритет, но всё равно требует авторизованного маршрута и полного журнала.
- `stop` не является обычным элементом очереди:
  - он обходит ожидающие обычные команды;
  - после подтверждения роботом прерывает текущее действие и очищает ожидающие команды с побочным эффектом;
  - переводит робот в фиксируемое состояние `safety_stopped`;
  - до отдельной авторизованной команды снятия блокировки разрешает только безопасные чтения состояния и повторный `stop`;
  - повторный `stop` идемпотентен и возвращает уже достигнутое состояние без второго физического действия.
- Для `stop` используется короткий срок жизни. Если робот не в сети или срок истёк, команда не остаётся на позднее выполнение, панель не показывает «остановлен» и прямо требует локальной проверки безопасности.
- Уже принятую обычную команду платформа не считает прерванной по факту отправки `stop`: её состояние меняется только после подтверждения робота. Робот обязан вернуть отдельный конечный результат прерванной команды с причиной `safety_stop`.
- Секреты, ключи, внутренние адреса и служебные URL не попадают в runtime-события и операторский интерфейс.
- Вводятся ограничения частоты команд по оператору и роботу.
- Журнал хранит безопасное описание действия, инициатора, время, переходы состояния и результат без секретных параметров.

## Порядок работ

### Этап 0. Подготовить чистую основу

Репозитории: `GOSHA_PLATFORM`, затем `GOSHA_FIRMWARE`.

1. Определить судьбу уже отправленных runtime-веток.
2. Предпочтительный путь — сначала принять их в основные ветки.
3. Если слияние откладывается, создать отдельные составные ветки команд поверх текущих runtime-веток и явно зафиксировать эту зависимость.
4. Использовать отдельные рабочие деревья:
   - `/home/max/worktrees/gosha/platform-operator-command-gateway`;
   - `/home/max/worktrees/gosha/firmware-operator-command-gateway`.
5. Не создавать Android-ветку, пока контракт команд не потребует изменения мобильного клиента.

Критерий выхода: у каждой затрагиваемой области есть отдельная чистая ветка и понятная база без смешивания с голосом, интерфейсной косметикой или reviewer/executor.

### Этап 1. Зафиксировать контракт и границы ответственности

Основной репозиторий: `GOSHA_PLATFORM`.

1. Добавить спецификацию `gosha.robot.command.v1`.
2. Утвердить первый список команд и схемы ответов.
3. Провести инвентаризацию того, что текущая прошивка действительно умеет возвращать и выполнять.
4. Зафиксировать правила срока жизни, повторов, отмены, идемпотентности и отдельный конечный автомат `stop`/`safety_stopped`.
5. Определить таблицу возможностей робота и правила несовместимых версий.
6. Зафиксировать миграцию со старого `cloud-mcp` и условия возврата на прежний режим.

Критерий выхода: контракт можно реализовать независимо в платформе и прошивке, не задавая друг другу скрытых предположений.

### Этап 2. Реализовать серверное ядро команд

Основной репозиторий: `GOSHA_PLATFORM`.

1. Создать отдельный модуль хранилища и конечного автомата команд.
2. Добавить внутренний шлюз с реестром авторизованных сессий роботов.
3. Реализовать:
   - постановку команды;
   - атомарное назначение конкретной сессии;
   - подтверждение принятия;
   - результат;
   - тайм-аут;
   - отмену до начала выполнения;
   - защиту от повторов.
4. Добавить операторские маршруты:
   - создание разрешённой команды;
   - чтение состояния конкретной команды;
   - ограниченный список последних команд робота;
   - отмена ещё не принятой команды.
5. Связать каждый переход с `gosha.runtime.event.v1`.
6. Добавить метрики очереди, задержки, ошибок, переподключений и просроченных команд.

Критерий выхода: имитатор робота проходит полный цикл команды, а повтор запроса не создаёт второе действие.

### Этап 3. Реализовать клиент команд в прошивке

Основной репозиторий: `GOSHA_FIRMWARE`.

1. Добавить неблокирующее соединение со шлюзом команд.
2. Не смешивать его жизненный цикл с OTA, голосом и аудиопотоком.
3. Реализовать проверку версии и объявление возможностей.
4. Реализовать обработчики:
   - `status`;
   - `battery`;
   - `stop`;
   - одного безопасного действия без движения.
5. Добавить локальный ограниченный журнал `idempotency_key`. Для команд с побочным эффектом он должен переживать не только короткое переподключение, но и перезапуск робота в пределах срока возможной повторной доставки.
6. Отправлять подтверждение принятия до выполнения и отдельный конечный результат.
7. Не блокировать основной автомат робота сетевыми повторами.
8. Добавить события соединения, выполнения, отказа и тайм-аута.

Критерий выхода: робот выдерживает потерю сети, повторную доставку и просроченную команду без зависания, повторного действия и перезапуска.

### Этап 4. Перевести рабочую страницу робота

Основной репозиторий: `GOSHA_PLATFORM`.

1. Оставить главный экран коротким пультом; команды размещать на отдельной рабочей странице выбранного робота.
2. Показывать оператору:
   - доступность собственного канала;
   - заявленные возможности робота;
   - очередь;
   - принятие;
   - выполнение;
   - конечный результат;
   - безопасную причину ошибки.
3. Не показывать внутренние адреса и ключи.
4. Для опасных действий использовать отдельное подтверждение.
5. Блокировать неподдерживаемые команды по таблице возможностей.
6. Обновлять состояние через общий операторский поток событий без ручной перезагрузки страницы.

Критерий выхода: две открытые панели видят один и тот же ход команды, но не могут выполнить её дважды одним нажатием.

### Этап 5. Провести безопасную миграцию

Репозитории: `GOSHA_PLATFORM`, `GOSHA_FIRMWARE`.

1. Ввести серверный переключатель маршрута по каждому роботу:
   - старый мост;
   - собственный шлюз в теневом режиме;
   - собственный шлюз как основной;
   - аварийный возврат.
2. В теневом режиме сравнивать только безопасные чтения `status` и `battery`.
3. Не отправлять команды с побочным действием сразу в два маршрута.
4. Сначала перевести один тестовый робот, затем `gosha-main`, затем остальные устройства.
5. После устойчивой приёмки убрать старый мост из основного пользовательского сценария, но сохранить ограниченный план возврата на период стабилизации.
6. Считать старый мост отключённым как основную зависимость только когда:
   - все активные роботы переведены на собственный шлюз или явно исключены из миграции;
   - `gosha-main` прошёл живую приёмку и контрольное окно без `P0/P1`;
   - панель больше не предлагает старый адрес как обычный путь;
   - возврат проверен, ограничен по времени и не допускает двойной отправки команд.
7. Удаление совместимого кода старого моста выполнять отдельной задачей после завершения окна стабилизации, а не одновременно с переключением боевого маршрута.

Критерий выхода: `gosha-main` подтверждённо отвечает через собственный шлюз, а старый `cloud-mcp` не является обязательной зависимостью панели.

### Этап 6. Проверить масштабирование и изоляцию

Основной репозиторий: `GOSHA_PLATFORM`.

Обязательные сценарии:

- несколько роботов одновременно;
- несколько панелей одного оператора;
- разные операторы с разными правами;
- два робота с одинаковыми локальными именами, но разными `robot_id`;
- переподключение робота во время активной команды;
- повтор того же `command_id`;
- переполнение очереди;
- просроченная команда;
- отказ хранилища;
- запоздавшее подтверждение старой сессии;
- одновременная обычная команда и аварийная остановка;
- повторный `stop` для уже остановленного робота;
- `stop` при отключённом роботе и позднее переподключение;
- запрет новых действий после `safety_stopped` до отдельного снятия блокировки;
- попытка доступа оператора к чужому роботу.

Критерий выхода: нет маршрутизации между чужими роботами, повторного побочного действия, неограниченной очереди и ложного статуса «выполнено».

### Этап 7. Живая приёмка и выпуск

1. Запустить полный набор автоматических тестов платформы и прошивки.
2. Выполнить независимую проверку ИИ-офисом.
3. На живом роботе по порядку проверить:
   - `status`;
   - `battery`;
   - безопасное действие;
   - `stop`;
   - потерю и возврат сети.
4. Для каждой команды подтвердить один `command_id`, один `correlation_id` и корректное конечное состояние.
5. Убедиться, что панель, робот и разрешённое приложение показывают согласованную картину.
6. Проверить отсутствие секретов и внутренних адресов в событиях и интерфейсе.
7. Обновить проектные и агентные контрольные точки.
8. Только после этого переводить собственный шлюз в основной режим.

Критерий выхода: четыре обязательные команды подтверждены физическим роботом, а отключение старого моста не ломает наблюдаемость, OTA, голос или мобильный API.

## Матрица обязательных проверок

| Проверка | Ожидаемый результат |
|---|---|
| Повтор одного `idempotency_key` | одно физическое действие и один конечный результат |
| Робот не в сети | команда остаётся ограниченно `queued` либо завершается `timed_out` |
| Возврат после истечения срока | просроченная команда не выполняется |
| Обрыв после принятия | повторное подключение не создаёт второе действие |
| Ответ старой сессии | отклоняется по поколению сессии |
| Неподдерживаемая команда | отказ до отправки роботу |
| Чужой `robot_id` | отказ в доступе без раскрытия существования устройства |
| Две панели | согласованное состояние без двойного запуска |
| `stop` при обычной команде в очереди | обходит очередь, а ожидающие побочные действия отменяются |
| `stop` при уже принятом действии | робот прерывает действие и отдельно подтверждает `safety_stop`; платформа не угадывает результат |
| Повторный `stop` | идемпотентный ответ `safety_stopped` без второго физического действия |
| Робот не в сети во время `stop` | короткий `timed_out`, нет позднего выполнения и ложного статуса «остановлен» |
| Команда после `safety_stopped` | разрешены только чтение, повторный `stop` и отдельное авторизованное снятие блокировки |
| Ошибка робота | безопасный код и понятный следующий шаг оператору |
| Потеря хранилища | нет ложного `completed` |
| События и журнал | нет токенов, URL, SSID и внутренних адресов |

## Что не входит в этот этап

- новый голос или движок синтеза речи;
- изменение имени пробуждения;
- косметическая перестройка главного экрана панели;
- произвольные команды движения;
- перенос профилей ИИ-агентов;
- объединение `GOSHA_PLATFORM` с `AI_ROBOT`;
- обязательные изменения Android-приложения без изменения его публичного контракта.

## Первый рабочий срез

Начинать следует с минимального сквозного пути:

1. `status` через имитатор робота;
2. `status` через живую авторизованную сессию робота;
3. событие `queued → running → completed`;
4. отображение результата на рабочей странице;
5. потеря соединения и честный `timed_out`;
6. после этого — `battery`, затем безопасное действие и последним `stop`.

Оценку календарных сроков нужно делать после инвентаризации возможностей прошивки на этапе 1. До этого любая точная дата будет скрывать главный риск: неизвестный объём адаптации текущего клиентского протокола робота.

## Определение полной готовности

Этап считается завершённым только когда:

- панель больше не зависит от старого моста для четырёх обязательных команд;
- результат подтверждает физический робот, а не только серверный шлюз;
- все переходы видны в общем runtime-контуре;
- команды изолированы по `robot_id`, оператору и сессии;
- повторная доставка безопасна;
- аварийная остановка имеет проверенный отдельный конечный автомат, приоритет и блокировку последующих действий;
- есть проверенный переход на собственный шлюз и документированный возврат;
- не сломаны публичный мобильный API, OTA, голос и существующая наблюдаемость;
- документация, тесты и контрольная точка обновлены одновременно с реальным поведением.
