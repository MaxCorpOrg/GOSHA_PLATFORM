# AGENTS.md

Это главный входной файл проекта `GOSHA_PLATFORM`.

## Как входить в проект

1. Прочитай `START_HERE_FOR_NEW_CHAT.md`.
2. Затем прочитай:
   - `docs/GOSHA_PROJECT_MAP_RU.md`
   - `docs/NEW_CHAT_CHECKPOINT_RU.md`
   - `docs/AGENT_CHECKPOINT_RU.md`
   - `docs/PROJECT_STATUS_RU.md`
3. Если работа идёт по конкретной папке, открой и её локальный `AGENTS.md`.

## Обязательный вход в новый чат

- Перед началом реальной работы агент обязан восстановить текущее состояние проекта, а не опираться на память.
- Для `GOSHA_PLATFORM` это обязательно включает:
  - чтение `START_HERE_FOR_NEW_CHAT.md`;
  - чтение `docs/NEW_CHAT_CHECKPOINT_RU.md`, `docs/AGENT_CHECKPOINT_RU.md`, `docs/PROJECT_STATUS_RU.md`;
  - проверку `git status --short --branch`;
  - проверку верхнего коммита через `git log --oneline -1`;
  - если задача относится к общему контуру `Гоша`, проверку свежей контрольной точки на рабочем столе.
- В первом содержательном ответе нового чата агент обязан явно сообщить:
  - текущую ветку;
  - текущий этап или стадию;
  - главный следующий шаг;
  - что относится именно к `GOSHA_PLATFORM`, а что вынесено в соседние репозитории.

## Правила общения с оператором

- Пиши отчёты, планы, объяснения, контрольные точки и техническую документацию нормальным русским техническим языком.
- Не используй русско-английский суржик в обычном тексте. Английский допустим только в командах, путях, именах файлов, названиях функций, переменных, веток, коммитов и в коде.
- Если без технического термина нельзя обойтись, сразу поясняй его по-русски.
- Пиши так, чтобы руководитель проекта, оператор и разработчик одинаково понимали смысл без дополнительных расшифровок.
- Для типовых слов используй такие формы:
  - `verified online` — подтверждённо в сети
  - `detect` — обнаружение
  - `branch` — ветка
  - `commit` — коммит
  - `push` — отправка изменений
  - `pull` — получение изменений
  - `scope` — область изменений
  - `handshake` — проверочный обмен запрос-ответ

## Главные правила

- `GOSHA_PLATFORM` живёт отдельно от `AI_ROBOT`.
- `GOSHA_PLATFORM` проектируется как масштабируемая платформа:
  - много роботов;
  - много профилей ИИ-агентов;
  - много OpenAI-совместимых провайдеров;
  - без жёсткой привязки к одному облаку или одной модели.
- Панель `Гоша` тоже проектируется как масштабируемая:
  - много ассистентов;
  - много движков синтеза речи;
  - много голосов;
  - много экранных профилей;
  - много профилей памяти и `MCP`;
  - без жёсткой привязки к одному экрану, одному голосу или одному имени пробуждения.
- Новые функции нельзя проектировать с расчётом на одного робота, одного оператора или одного поставщика ИИ.
- Не смешивай рабочие каталоги, unit-файлы `systemd` и `env`-файлы `GOSHA` с `/opt/ai_robot`.
- В git идут только исходники, документация, инструкции по развёртыванию и отслеживаемые скрипты.
- Всё локальное состояние должно жить под `local_only/` и не попадать в коммиты.
- Перед заметными изменениями проверь `git status --short --branch` и последнюю контрольную точку.

## Правила веток и `git worktree`

- Для параллельных направлений используй отдельные рабочие деревья `git worktree`, а не одну общую грязную копию репозитория.
- Канонический путь ручных рабочих деревьев разработчика:
  - `/home/max/worktrees/gosha/<контур>-<задача>`
- Для новых ручных задач в `GOSHA_PLATFORM` обычной базой считай `origin/main`, если только задача не продолжает уже существующую профильную ветку.
- Для ручных рабочих веток используй такие префиксы:
  - `feature/` — продуктовая функция
  - `hotfix/` — срочное исправление
  - `release/` — подготовка выпуска
- Не смешивай в одной рабочей ветке разные направления без явной необходимости:
  - панель оператора
  - голос и `TTS`
  - контракты `mobile API`
  - reviewer/executor
- Автоматические рабочие деревья executor живут отдельно:
  - `local_only/oauth_executor_worktrees`
  Их нельзя использовать как ручные рабочие копии разработчика.
- Перед созданием нового `worktree` либо закоммить текущие изменения, либо перенеси их в отдельную ветку, чтобы не разносить незавершённую работу между задачами.

## Что обновлять после значимой задачи

- `docs/PROJECT_STATUS_RU.md`
- `docs/AGENT_CHECKPOINT_RU.md`
- `docs/NEW_CHAT_CHECKPOINT_RU.md`, если изменилась короткая контрольная точка входа
- локальный `AGENTS.md`, если изменилась зона ответственности папки
- свежую контрольную точку на рабочем столе, если она используется как внешний входной файл для следующего чата

## Review guidelines

- Считай `P0` любую утечку секретов, токенов, содержимого `GOSHA_API/`, `/opt/gosha_platform/runtime/env/providers.env` или других рабочих ключей поставщиков ИИ.
- Считай `P0` любое изменение, которое ломает публичные маршруты `mobile API`, операторские маршруты панели, живой `OTA`-контур или live-probe робота без явного и задокументированного плана миграции.
- Считай `P1` возврат зависимости на `xiaozhi.me`, смешивание `GOSHA_PLATFORM` с `AI_ROBOT` или проектирование нового кода только под одного робота, один голос или одного поставщика ИИ.
- Считай `P1` показ оператору прямых `OTA`-адресов, `WebSocket`-адресов, внутренних endpoint-деталей или другой служебной инфраструктуры, которая должна оставаться внутри сервисного контура.
- Считай `P1` изменение, которое ломает разделение операторского UX: главный экран — короткий пульт, рабочая страница робота — отдельное место действий и диагностики.
- Считай `P1` изменение реального поведения проекта без обновления `docs/PROJECT_STATUS_RU.md`; если меняется маршрут входа для следующего агента, требуй также обновление `docs/AGENT_CHECKPOINT_RU.md` и `docs/NEW_CHAT_CHECKPOINT_RU.md`.

## Важные зоны

- `platform/` — панель, маршруты `mobile/operator API` и логика платформы `Гоша`
  Основной операторский UX здесь теперь такой:
  - на главном экране — карточки роботов;
  - по нажатию открывается отдельная рабочая страница выбранного робота;
  - тяжёлые каталоги и служебные панели скрыты, пока оператор не откроет их явно
  - прямые прошивочные ссылки, OTA-URL и служебные endpoint-детали не показываются в открытом интерфейсе
  - в рабочей странице робота нельзя снова смешивать:
    - главные статусы;
    - кнопки управления;
    - подключение;
    - личность, модель и голос;
    - клиент, память и инструменты;
    - след устройства
  - если меняется панель робота, сначала сохраняй это разделение, а уже потом улучшай конкретные блоки
- `/home/max/GOSHA_MOBILE` — отдельный мобильный клиент `Гоша`; он живёт вне этого репозитория, но зависит от контрактов `mobile API` этой платформы
- `/home/max/GOSHA_FIRMWARE` — отдельный репозиторий прошивки `Гоша`; он живёт вне этого репозитория, но зависит от OTA, голоса и контрактов платформы
- `platform/gosha_agent_gateway.py` — отдельная внутренняя служба масштабируемого шлюза ИИ-агентов
- `platform/gosha_assistant_store.py` — составные профили ассистента, голоса, памяти, экрана, пробуждения и базы знаний
- `platform/gosha_assistant_store.py` — составные профили ассистента, движков синтеза речи, голоса, памяти, экрана, пробуждения и базы знаний
- `platform/gosha_agent_store.py` — слой хранения профилей агентов и привязки к роботам поверх файлового слоя хранения
- `backend/` — `docker compose` и шаблон `env` для совместимого серверного узла платформы `Гоша`
- `backend/overrides/` — репозиторные переопределения голосового и совместимого серверного контура; здесь нельзя делать ручные контейнерные хаки вне git
- `ops/` — установка на сервер, наблюдатель и unit-файлы `systemd`
- `bin/` — локальные вспомогательные скрипты разработчика
- `oauth_reviewer/` — внешний ручной сервис проверки `Pull Request` через `GitHub OAuth`; он не должен мутировать git сам по себе и не должен хранить `OpenAI`-ключи в репозиторных secrets
- `oauth_executor/` — локальный исполнительный агент `Codex`; он читает замечания по PR, правит отдельную рабочую копию через `git worktree`, запускает проверку, делает коммит и отправляет изменения только в head-ветку PR
- `docs/` — контрольные точки, рабочие инструкции и документы передачи состояния
- `docs/GOSHA_PROJECT_MAP_RU.md` — главная карта всех связанных контуров: платформа, сервер, прошивка, мобильный клиент, голоса и документы
- `docs/GOSHA_ASSISTANT_CONTROL_PANEL_SPEC_RU.md` — спецификация собственной панели настройки ассистента, голоса, экрана, памяти и имени пробуждения `Гоша`
- `/opt/gosha_platform/runtime/env/providers.env` — серверный файл с ключами внешних поставщиков ИИ; его нельзя публиковать и нельзя описывать как часть git-репозитория
- `GOSHA_API/` — только локальный секретный каталог разработчика; он не является частью продукта и не должен уходить в git
