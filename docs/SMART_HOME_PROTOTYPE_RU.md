# Smart Home: аудит и изолированный прототип

Дата аудита и локальных проверок: 18 октября 2026 года.
Статус: программный прототип в отдельной ветке, НЕ установлен и НЕ подключён
к принятому разговору Гоши. Физические устройства не переключались.

## 1. Что проверено в проекте

Основа — доступный снимок GOSHA_PLATFORM. Каталог подключённых проектов
предупреждает: он старее последних принятых локальных изменений. Поэтому
сведения ниже относятся к прочитанным исходникам, а не к установленному роботу.

- `platform/gosha_voice_router.py`: аутентификация голосового WebSocket по
  токену привязки робота, совместимый backend и отдельный Live-маршрут.
  `RobotLiveBridge` создаёт `DeviceTools`, публикует определения функций,
  запускает `LiveToolRunner`. Устройство передаёт MCP через голосовое соединение.
- `platform/gosha_live_tools.py`: явный разрешённый список функций устройства,
  обнаружение функций, строгие аргументы, разделение подтверждённого результата
  и неизвестного исхода. Есть функции громкости, яркости экрана, темы, батареи,
  состояния и движений. **Это не управление домашними устройствами**.
- `platform/gosha_agent_gateway.py`: шлюз профилей и запросов модели:
  GET `/healthz`, `/v1/providers`, `/v1/profiles`, `/v1/models`;
  GET/POST `/v1/robots/<robot>/active-profile`, POST `/v1/chat/completions`.
  Не следует превращать этот шлюз в публичный API управления домом.
- `platform/gosha_assistant_store.py` и `gosha_agent_store.py` участвуют в
  настройках профилей по вызовам маршрутизатора; полный аудит их безопасности
  и всех маршрутов панели в эту итерацию не входит.
- `docs/GOSHA_PROJECT_MAP_RU.md` описывает разделение платформы, прошивки и
  мобильного клиента. Для этого прототипа не нужны изменения прошивки или USB.

## 2. Выбранная архитектура

Голос Гоши → выделенный обработчик Smart Home → проверка разрешённого
устройства и действия → локальный Home Assistant → Aqara.

Home Assistant представляет устройство как entity — именованный объект,
например `light.kitchen`. Только вручную разрешённые объекты доступны модулю.
Приоритет — Home Assistant, чтобы не создавать отдельную зависимость
от облака Aqara для каждого типа устройств.

Выбор подключения Aqara после инвентаризации:

1. Для поддерживаемых устройств/хаба с Matter — интеграция Matter в HA.
   Официальная страница Aqara в HA подтверждает локальное взаимодействие
   Matter и содержит перечень сертифицированных моделей. Это НЕ гарантия
   экспорта всех дочерних устройств или фирменных функций любого хаба.
2. Для совместимого HomeKit-хаба — HomeKit Device. Это импорт в HA,
   а не HomeKit Bridge (обратный экспорт). Нужно проверить модель,
   код сопряжения и существующие привязки; смена контроллера влияет на дом.
3. Для Zigbee без подходящего хаба — ZHA с совместимым координатором,
   только после согласования миграции: Zigbee-устройство состоит лишь в одной
   Zigbee-сети. Совместимость конкретных моделей требует проверки.
4. Прямой официальный облачный API Aqara — резервный путь. Возможность
   регистрации приложения, регион, доступные методы и разрешения не проверены;
   этот прототип не использует и не заявляет реализацию облачного API Aqara.

Управление: POST `/api/services/<domain>/<service>`, а НЕ запись искусственного
состояния в `/api/states`. Чтение: GET `/api/states/<entity>`.
Для непрерывных обновлений позднее нужен WebSocket HA, в этой версии его нет.

## 3. Реализовано

Файлы `smart_home/core.py`, `smart_home/demo.py`, `smart_home/test_core.py`:

- свет: включение, выключение, яркость 0–100%;
- шторы: открыть, закрыть, остановить, положение 0–100%;
- климат: целевая температура в °C, индивидуальный диапазон в пределах 5–35°C,
  по умолчанию 16–28°C, проверка единиц и границ объекта в HA;
- датчики и бинарные датчики: чтение состояния, единицы, времени обновления;
- точный разбор ограниченной русской грамматики, имена и синонимы из реестра;
- неоднозначная команда отклоняется; свободные URL, произвольные службы,
  замки, сигнализация, пакеты команд не поддерживаются;
- шторы требуют класса curtain/shade/blind; гаражные ворота запрещены;
- безопасный режим по умолчанию: изменение только планируется, без сети;
- HTTPS с обычной проверкой сертификата; HTTP только для явно разрешённой
  петли на том же компьютере, например тестовый сервер `127.0.0.1`;
- токен только в заголовке запроса, без печати, прокси и перенаправлений;
- таймаут, ограниченный размер ответа, отсутствие автоматического повтора;
- повтор одного идентификатора голосового запроса не вызывает новую запись
  в пределах экземпляра модуля. Максимум 256 запросов; после перезапуска
  повторять физические команды нельзя. Это не постоянный журнал операций.

`Provider` — интерфейс заменяемого поставщика; это задел под другие системы,
а не готовые интеграции Яндекса, Xiaomi или Tuya. Matter уже возможен на стороне
HA при совместимых устройствах, собственного контроллера Matter здесь нет.

Функция `call(name, encoded)` подготовлена в формате вызова существующего
обработчика функций. Полного адаптера Live-сессии (определения функций,
обнаружение, разделение домов/пользователей, жизненный цикл, отключение)
пока нет. Действующий маршрутизатор намеренно не изменён.

### Статусы, которые нельзя путать

- `planned`: команда разобрана, но не отправлена;
- `accepted`: HA ответил на вызов; физический результат НЕ подтверждён;
- `observed`: прочитано состояние HA; дата обновления передаётся отдельно,
  свежесть и физическая достоверность показания не гарантируются;
- `unknown`: нет надёжного ответа; не повторять автоматически;
- `rejected` / `unavailable`: команда отклонена или чтение недоступно.

## 4. Запуск без робота и без токенов

Из корня проекта, Python 3.11 или новее, без внешних библиотек:

```sh
python3 -B -m unittest smart_home.test_core -v
python3 -B -m smart_home.demo 'Гоша, включи свет на кухне'
python3 -B -m smart_home.demo 'открой шторы в спальне на 40 процентов'
python3 -B -m smart_home.demo 'установи температуру климат в комнате на 22 градуса'
```

Демонстрация не подключается к HA, не изображает реальные показания датчиков.
Фразы пока шаблонные, включая неестественные падежи для числовых команд.
Для естественной речи следующий этап — контролируемое сопоставление намерений
с тем же валидатором, а не выполнение произвольного текста модели.

Для будущего стенда нужно создать `HomeAssistant(url, token)` и
`SmartHome(provider, devices, writes_enabled=True)` в отдельном тестовом
процессе после разрешения. Токен передавать из защищённого хранилища,
не помещать в репозиторий, примеры, историю чата или командную строку.
Демо специально не предоставляет флаг физического исполнения.

## 5. Проверки и ограничения

Локально прошли **19 тестов**: маршруты и тела запросов пяти категорий,
русские команды, пределы значений, неизвестные устройства, неоднозначность,
запрет опасных классов, недоступность, °C/°F, запрет повторов при потере ответа,
непередача произвольных атрибутов в ответ, реальный HTTP на тестовой петле,
авторизация, HTTP 401, запрет перенаправления. Используется фиктивный токен.
Добавлен отдельный GitHub workflow тестов; удалённый запуск ещё не подтверждён.

Полная штатная проверка `bin/ci_validate.sh` запускалась, но остановилась на
шаге 2: выданная рабочая копия не содержит `.git`, а сценарий использует
`git ls-files`. Это НЕ успешная полная сборка. Каталог дополнительно сообщает,
что доверенные проверки проекта не настроены. Нужна отдельная настройка,
без ослабления критериев приёмки. Тесты робота/реального HA не проводились.

Остаются: подтверждение физических результатов и допустимого времени ожидания;
постоянный журнал запросов; таймауты/повторное подключение в живой сети;
ограничение частоты; раздельные права домов и пользователей; поддерживаемые
режимы климата/шаг температуры; проверка свежести датчиков; события HA;
более естественная речь; разрешения на опасные сценарии. Токен HA сам по себе
не считается гранулярным ограничением доступа — разрешённый список модуля
и изоляция стенда обязательны. Прототип не готов для публичного доступа.

## 6. Необходимые данные и приёмка

1. Владелец/сопровождающий платформы: предоставить актуальную принятую версию
   исходников или безопасный экспорт и список отличий. Результат — сверенная база.
2. Владелец дома: модели хаба/устройств Aqara, регион, версии, текущие привязки;
   наличие и версия HA, топология сети, разрешённые объекты и температурные
   пределы. Результат — таблица совместимости и точная схема подключения.
3. Гео: после сверки базы подготовить opt-in адаптер голоса и тесты на
   имитаторе с существующим LiveToolRunner. Результат — кандидат без влияния
   на разговор по умолчанию и без управления сервоприводами робота.
4. Владелец + Гео: согласовать изолированный стенд и защищённую передачу
   отдельного токена HA; начать с чтения датчика, затем одной лампы,
   отдельно шторы и климат. Результат — журнал реальных проверок, не обещание.
5. Владелец: отдельное разрешение на внедрение после ревью и полной проверки.
   Результат — управляемый выпуск с откатом, не автоматическая установка.
