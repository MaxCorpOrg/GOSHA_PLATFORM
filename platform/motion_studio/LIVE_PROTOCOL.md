# Live: локальная сессия настройки

Протокол `gosha.motion.live.v1` предназначен для собственного обработчика
прошивки Гоши. Сообщения Live одинаковы для двух транспортов: прямой Wi-Fi
WebSocket робота `:8080/ws` и локальная USB-служба на этом компьютере. Это
отдельное пространство сообщений; перехода на старые MCP motion/servo sequence
tools нет. Отсутствие ответа означает несовместимость, а не разрешение движения.

## Состояние поставки

Клиент находится в этом модуле. Прошивочный обработчик для первого Live-теста
ног был подготовлен в GOSHA_FIRMWARE, ветка `codex/motion-live-20260906` от
точного установленного safe-neutral `baf0323d17db9f0635cf9ae64d79eb6f3c19af2c`.
Отдельное расширение 2026-09-07 добавляет в клиент ожидание включения правой
руки и пошаговую проверку одного выбранного сустава. Текущее расширение
2026-09-07 добавляет выбор транспорта USB/Wi-Fi и локальную USB-службу для
браузеров без WebSerial. Эта клиентская сборка сама не устанавливает прошивку,
не открывает сеть робота и не запускает движение.

Исторический первый аппаратный набор ограничен четырьмя каналами ног/ступней.
Новый праворукий набор разрешает только `arm_positive_x` и те же четыре
сустава ног/ступней. Левая рука физически отключена и в Live остаётся
недоступной. Правая рука привязана к аппаратному каналу GPIO12 с нейтралью
135°, но физическое направление и механическая модель ещё подтверждаются
оператором.

## Проверочный обмен и доступ

Каждое сообщение имеет поле `protocol: "gosha.motion.live.v1"`.
Клиент отправляет `op: "hello", request_id`; до ответа других команд нет.
Ответ `op: "capabilities"` должен вернуть тот же `request_id`.
Закрытый аппаратный профиль отвечает `motion_allowed:false` и кодом причины.

Для разрешённого устройства клиент требует все поля:

| Поле | Проверка |
|---|---|
| `motion_allowed`, `calibrated` | В проверенном режиме оба равны `true`; в `commissioning` и `commissioning_right_arm` допускается `calibrated:false` по правилам ниже |
| `profile_id` | `gosha-preview-v1` |
| `calibration_id` | SHA-256 проверенного профиля, 64 строчные hex-цифры |
| `auth_required` | `true` |
| `stop_mode` | `hold_setpoint` |
| `watchdog_ms` | 100–500 мс; у первого обработчика 300 мс |
| `max_rate_hz` | 5–20 Гц, интервал не больше половины watchdog |
| `joint_limits` | Неповторяющиеся известные `id`, `min`, `max`, `max_speed_dps` |
| `commanded_pose` | Все шесть известных суставов, относительные градусы |
| `feedback` | Отдельные флаги `measured_position` и `imu` |
| `right_arm_initialized` | Только для `commissioning_right_arm`; до включения `false`, после включения `true` |

Границы должны укладываться в визуальный профиль, скорость — до 30°/с.
Приложение дополнительно ограничивает настройку диапазоном 1–15°/с.
Нормы движения проверяет **сама прошивка**, а не только браузер.

### Первичная проверка приводов

Для первого аппаратного теста предусмотрен отдельный явно ограниченный
вариант: `commissioning:true`, `calibrated:false`. Он не подтверждает
механическую калибровку, сторону модели или направление вращения. Отсутствие
этой метки по-прежнему требует `calibrated:true`; противоречивые поля отклоняются.

В этом варианте допускаются ровно четыре привода ног/стоп, пределы только
`-1…+1°`, скорость только `1°/с`, watchdog `300 ms`. За одну сессию можно
изменять один сустав с отклонением не больше `1°` от команды на момент ARM;
остальные сохраняют начальные команды. Возврат первого сустава не разрешает
переключиться на второй в той же сессии. Проверки действуют и в клиенте,
и в прошивке. Ключ доступа, владение сессией, ACK и STOP остаются обязательными.

Редактор явно показывает «Первичная проверка приводов», фиксирует скорость
и запрещает воспроизведение целого движения. Кнопка «Взять текущие команды
робота» переносит последние подтверждённые уставки в редактируемую позу;
сама она не сохраняет движение и не посылает команд приводу. При первом
движении оператор поддерживает корпус и наблюдает реальный привод.

### Проверка правой руки

Для правой руки используется отдельный режим `mode:"commissioning_right_arm"`,
`commissioning:true`, `calibrated:false`. Это не калибровка и не подтверждение
баланса. До явного включения робот отвечает на `hello` состоянием:

```json
{
  "protocol": "gosha.motion.live.v1",
  "op": "capabilities",
  "request_id": "<из hello>",
  "mode": "commissioning_right_arm",
  "commissioning": true,
  "calibrated": false,
  "motion_allowed": false,
  "reason": "right_arm_initialization_required",
  "right_arm_initialized": false
}
```

Остальные поля безопасности остаются обязательными: `profile_id`,
`calibration_id`, `auth_required:true`, `stop_mode:"hold_setpoint"`,
`watchdog_ms:300`, `max_rate_hz` не больше 20, `joint_limits`,
`commanded_pose` и `feedback`. До включения `commanded_pose.arm_positive_x = 0`
является только логическим placeholder. Клиент показывает его как «Нет команды /
не включена», не как измеренный угол.

Клиент принимает ровно пять активных суставов:

| Сустав | Предел | Скорость |
|---|---:|---:|
| `arm_positive_x` | `-5…+5°` | `1°/с` |
| `leg_negative_x` | `-1…+1°` | `1°/с` |
| `leg_positive_x` | `-1…+1°` | `1°/с` |
| `foot_negative_x` | `-1…+1°` | `1°/с` |
| `foot_positive_x` | `-1…+1°` | `1°/с` |

`arm_negative_x` в этом режиме отсутствует. В одной сессии можно изменять
только один физический сустав: правую руку не больше чем на 5° от команды на
момент ARM, ногу или стопу не больше чем на 1°. Все остальные суставы должны
сохранить начальную команду. Эти проверки применяются к исходящим `pose`,
входящим `ack` и `stopped`.

Кнопка «Включить правую руку» появляется после ввода ключа доступа и отправляет
отдельное сообщение вне ARM:

```json
{
  "protocol": "gosha.motion.live.v1",
  "op": "initialize_right_arm",
  "request_id": "<новый request_id>",
  "calibration_id": "<текущий calibration_id>",
  "access_key": "<введённый ключ>"
}
```

Успешный ответ — новый `capabilities` с тем же `request_id`,
`right_arm_initialized:true` и `motion_allowed:true`. После него клиент переходит
в состояние готовности, но не открывает ARM и не отправляет `pose`. При тайм-ауте
инициализации клиент не повторяет команду и сообщает: «Сессия движения не
открыта; подтверждение удержания правой руки не получено, состояние
неизвестно».

В интерфейсе есть пошаговый тест: оператор выбирает доступный сустав, видит
последнюю подтверждённую команду, выбирает знак `+` или `−`, видит целевую
команду и удерживает кнопку выполнения. Подготовка цели не двигает робота и не
меняет сохранённые движения в браузерной библиотеке. Для правой руки первый
операторский шаг по умолчанию — `-5°`; при нейтрали 135° это соответствует
целевому углу сервопривода 130° в профиле с направлением `+1`.
После начала удержания клиент фиксирует выбранный сустав и абсолютную цель шага
до отпускания и подтверждения STOP. Промежуточные ACK, например `0 → -1 → ... →
-5°`, обновляют текущую подтверждённую команду, но не пересчитывают отображаемую
цель как следующий шаг.

Нажатие «Открыть сессию» отправляет `op:"arm"`, новый `request_id`,
`calibration_id` и `access_key`. Ключ выдаётся при отдельной локальной
подготовке проверенного профиля робота. Он не сохраняется в библиотеку,
экспорт движения, журналы приложения или Git. Сеанс использует локальную
доверенную сеть; данный WebSocket не шифрует транспорт.

Успешный `armed` возвращает новый непредсказуемый `session_id`, совпадающие
`request_id` и `calibration_id`. Само открытие сессии не задаёт новую позу.
Устройство допускает одного владельца и связывает сессию с его соединением.

## USB-транспорт

USB не меняет JSON-контракт Live. Браузер подключается только к локальной
службе на `http://127.0.0.1:5177`; сама служба общается с прошивкой строками:

```text
@GOSHA-LIVE:{"protocol":"gosha.motion.live.v1","op":"hello","request_id":"..."}
```

Каждая строка заканчивается `\n`. JSON запроса после префикса ограничен
4096 байтами, JSON ответа — 16384 байтами. Служба принимает только сообщения с
`protocol:"gosha.motion.live.v1"`, проверяет префикс ответов и игнорирует
прочие serial-строки как boot/log output. Разделённые во времени serial-чанки
собираются до `\n`; слишком длинный или незавершённый кадр закрывает transport
с ошибкой.

Список портов — read-only endpoint `/ports`. В него попадают только USB serial
устройства с VID/PID `303a:1001`; локальные имена файлов устройств и произвольные
пути наружу не отдаются. Браузер получает только непрозрачный `port_id`, метку
для оператора и VID/PID. Serial-порт не открывается при перечислении и не
открывается до явного нажатия **Подключить по USB**.

При подключении браузер открывает WebSocket
`ws://127.0.0.1:5177/live?port_id=<opaque-id>`. Служба принимает запросы только
с точным Origin редактора `http://127.0.0.1:5176`, работает на loopback и
допускает одного владельца serial-порта. Перед открытием port настроен как
exclusive, `115200`, `write_timeout` меньше watchdog, DTR/RTS сняты; если
безопасная настройка не подтверждается, порт не открывается. Служба не делает
reset, не toggles DTR/RTS для autoreset и не запускает helper motion-callback.

Первым сообщением WebSocket должен быть обычный Live `hello`. Если устройство
отсутствует, занято или не возвращает корректный `capabilities`, клиент получает
отдельные ошибки `usb_device_absent`, `usb_port_busy` или `firmware_nohello`.
Очередь исходящих кадров ограничена по размеру и возрасту; поздние `pose` не
досылаются. При закрытии WebSocket, serial-ошибке или ошибке протокола служба
закрывает serial, очищает очередь и не выполняет autoresume/replay.

## Передача поз и остановка

Пока оператор удерживает разрешение движения, клиент отправляет:

```json
{
  "protocol": "gosha.motion.live.v1",
  "op": "pose",
  "session_id": "<текущая сессия>",
  "seq": 1,
  "target": { "leg_negative_x": 0, "leg_positive_x": 0, "foot_negative_x": 0, "foot_positive_x": 0 },
  "speed_dps": 10
}
```

Значения в примере описывают формат, а не разрешённую аппаратную позу.
`target` содержит только активные суставы из проверенного ответа робота. В
`commissioning_right_arm` туда входит `arm_positive_x` и четыре сустава
ног/ступней; `arm_negative_x` не отправляется.
Углы не преобразуются в аппаратные каналы в браузере: это ответственность
проверенного прошивочного профиля, включая нейтраль, знак и подстройку.

Клиент хранит последнюю цель и не отправляет следующую до ACK предыдущей.
На стороне робота также нет очереди макродвижений: есть текущая цель и
ограниченный по скорости неблокирующий шаг. При отсутствии удержания
открытая сессия отправляет только `keepalive` с `session_id` и `seq`.
Все последовательные номера строго возрастают; запоздалые/чужие сообщения
не должны продлевать аппаратный срок ожидания связи.

`ack` возвращает `session_id`, `seq`, `commanded_pose`, а также
`measured_pose:null` и `tilt:null`, если измерителей нет. `commanded_pose`
означает программно заданные углы PWM, не измеренные положения валов.
3D в активном Live показывает последнюю подтверждённую команду, либо
измеренные углы только при настоящей поддержке обратной связи.

Отпускание кнопки/пробела, Esc, смена окна, скрытие вкладки, изменение
выбранного движения или ошибка завершают удержание. `stop` содержит
`session_id` и следующий `seq`; `stopped` подтверждает сброс сессии и возвращает итоговые `commanded_pose`,
`measured_pose` и `tilt` по тем же правилам, что ACK.
Ручное отключение и переключение в 3D также ожидают этот ответ.
До подтверждения интерфейс пишет «Останавливаем». При отсутствии ответа
он сообщает, что состояние робота неизвестно. Повторного автоматического
подключения, возобновления или возврата Home нет.

Независимый аппаратный watchdog останавливает изменение уставок при
потере владельца/валидных пакетов. Стратегия остановки — сохранить последнюю
команду PWM, не отпускать опору и не запускать новую позу.
Это не аппаратная кнопка снятия питания и не алгоритм равновесия.

## Воспроизведение и измерения

Для Live-воспроизведения вся последовательность проверяется по диапазонам.
Шкала замедляется по самому быстрому участку, с учётом пикового наклона
плавной интерполяции и заданной скорости. Переходы типа `hold` отклоняются.
В обоих commissioning-режимах воспроизведение всей последовательности
запрещено; повторение всей последовательности в Live автоматически не
запускается.

У текущего `gosha-v1` нет подтверждённого измерения углов/IMU, поэтому
равновесие проверяется наблюдением физического робота после механического
допуска. Видеонаблюдение, IMU, датчики тока/контакта опоры и автоматическая
стабилизация в эту реализацию не входят. Флаги отсутствующих измерений не
подменяются расчётом, нулём или признаком «устойчиво».

## Программная проверка

`npm test` использует подставной транспорт и управляемые часы, не робот.
Проверяются отказ старой/no-motion прошивки до ARM, границы, отсутствие
неявной передачи поз, отдельная инициализация правой руки без автоматического
ARM, один сустав и шаг `5°/1°`, фиксированное отображение активного шага при
промежуточных ACK, последняя цель без очереди, номера и подтверждения, потеря
связи, stop timeout, отмена ARM, старые ответы, ошибочные ACK/STOP и отсутствие
ложных измерений. `npm run test:bridge` проверяет локальную USB-службу на
подставных serial/HTTP/WebSocket: фильтр `303a:1001`, скрытие путей, Origin,
одного владельца, DTR/RTS/exclusive до открытия, split-ответы, boot logs,
ограничения размеров, тайм-аут hello, busy/absent/nohello errors, отсутствие
безграничного flush и очистку очереди без replay. Браузерные и физические
прогоны отдельно не выполнены.

Справочные API: [WebSocket](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket),
[видимость страницы](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API).
