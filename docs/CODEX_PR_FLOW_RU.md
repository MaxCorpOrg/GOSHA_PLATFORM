# CODEX PR FLOW

Этот документ фиксирует безопасный контур работы `Codex` для `GOSHA_PLATFORM`:

- код делается в отдельной рабочей ветке;
- изменения не отправляются прямо в защищённую базовую ветку;
- создаётся `Pull Request`;
- `GitHub Actions` запускает проверку репозитория;
- `Codex` и при желании внешний OAuth-сервис проверки смотрят изменения и оставляют замечания;
- отдельный локальный OAuth-executor может автоматически применить правки по замечаниям и отправить их обратно в head-ветку PR;
- после правок проверки и review проходят повторно;
- только потом изменения можно сливать в защищённую базовую ветку.

## Что добавлено в репозиторий

- локальный и CI-скрипт проверки:
  - `bash bin/ci_validate.sh`
- скрипт старта рабочей ветки:
  - `bash bin/start_codex_pr_branch.sh <имя-задачи> [базовая-ветка]`
- обязательная GitHub-проверка:
  - `.github/workflows/repo-validation.yml`
- шаблон `Pull Request`:
  - `.github/pull_request_template.md`
- правила проверки для официального review `Codex`:
  - `AGENTS.md`
- внешний ручной OAuth-сервис проверки:
  - `oauth_reviewer/`
  - `docs/GOSHA_OAUTH_REVIEWER_RUNBOOK_RU.md`
- внешний локальный OAuth-executor:
  - `oauth_executor/`
  - `docs/GOSHA_OAUTH_EXECUTOR_RUNBOOK_RU.md`

## Как работать с новой схемой

1. Создай рабочую ветку:

```bash
cd /home/max/GOSHA_PLATFORM
bash bin/start_codex_pr_branch.sh operator-ux-pass main
```

2. Сделай правку и локально проверь её:

```bash
bash bin/ci_validate.sh
```

3. Отправь рабочую ветку в `origin` и открой `Draft PR`.

4. Дождись статуса `repo-validation`.

5. Основная AI-проверка кода для OAuth-режима:
   - официальный review `Codex` в GitHub.

6. После замечаний есть два пути:
   - ручной: правки в ту же ветку вносит автор ветки;
   - автоматический: `oauth_executor` сам читает замечания, правит отдельную рабочую копию, делает коммит и отправляет изменения в ту же head-ветку PR.

7. Дождись повторного зелёного статуса и только потом переводи PR в готовый к слиянию.

## Официальный review Codex

По официальной документации OpenAI `Codex` умеет:

- автоматически смотреть `Pull Request`;
- реагировать на комментарий `@codex review`;
- получать follow-up-команды вроде `@codex fix the P1 issue`;
- опираться на `AGENTS.md` и его `Review guidelines`.

Для этого вне репозитория нужно включить две вещи:

1. Подключить репозиторий к `Codex cloud`.
2. В настройках `Codex` включить:
   - `Code review`
   - при желании `Automatic reviews`

Это не тот же контур, что `OAuth` для пользовательских `GPT Actions`.
Для review в GitHub важна именно интеграция `Codex` с репозиторием и доступ к `Codex cloud`, а не `OAuth`-авторизация к OpenAI API.

## Если нужен именно OAuth

Если требование жёсткое и в репозитории нельзя хранить секрет `OPENAI_API_KEY`, то встроенный `GitHub Action` с `PR-Agent` сюда не подходит.

Причина простая:

- по официальной документации OpenAI, сам `OpenAI API` аутентифицируется API-ключами;
- `OAuth` в экосистеме OpenAI относится к пользовательскому входу в `GPT Actions` и к доступу к вашему API, а не заменяет серверный `OPENAI_API_KEY` для model calls.

Поэтому у OAuth-режима здесь две реалистичные схемы:

1. Использовать официальный review `Codex` в GitHub как основной сервис AI-проверки кода.
   В этом случае секрет `OPENAI_API_KEY` не хранится в secrets этого репозитория.
2. Если нужен второй сервис проверки в духе `PR-Agent`, выносить его во внешний сервис:
   - доступ к GitHub давать через `GitHub App` или `GitHub OAuth`;
   - если нужен ручной запуск из `ChatGPT`, поверх этого можно дать вашему сервису `OAuth` через `GPT Actions`;
   - если сервис вызывает `OpenAI API` напрямую, ключ всё равно должен лежать на серверной стороне вне репозитория;
   - если сервис использует уже авторизованный локальный `Codex CLI`, отдельный HTTP-ключ для reviewer может не понадобиться.

В этом репозитории уже создан первый каркас такого внешнего сервиса:

- код:
  - `oauth_reviewer/`
- локальный запуск:
  - `bash bin/run_local_oauth_reviewer.sh`
- runbook:
  - `docs/GOSHA_OAUTH_REVIEWER_RUNBOOK_RU.md`

На этой машине reviewer уже переведён на локальный `Codex CLI`, если `codex login status` подтверждает действующий вход.

Для полного цикла после замечаний в этом же репозитории добавлен и отдельный исполнитель:

- код:
  - `oauth_executor/`
- локальный запуск:
  - `bash bin/run_local_oauth_executor.sh`
- runbook:
  - `docs/GOSHA_OAUTH_EXECUTOR_RUNBOOK_RU.md`

Именно поэтому в этом репозитории оставлен разделённый контур:

- проверяющий сервис только пишет замечания;
- executor только вносит правки и отправляет изменения в head-ветку PR;
- секретозависимый `PR-Agent` workflow внутри репозитория убран.

## Как выглядит полный автоматический цикл

1. Мы пишем код в отдельной ветке и открываем `Pull Request`.
2. `GitHub Actions` запускает `repo-validation`.
3. Сервис проверки публикует замечания:
   - официальный review `Codex` в GitHub;
   - или внешний `oauth_reviewer`.
4. `oauth_executor` получает событие `pull_request_review` по webhook.
   Постоянный внешний путь для GitHub теперь идёт через серверную панель:
   `http://151.241.228.232:18876/hooks/oauth-executor/github`
   Если `COMMENTED` review содержит только чистый итог без inline-замечаний, webhook пропускает его и не тратит запуск executor.
5. Сервис поднимает отдельную рабочую копию в `local_only/oauth_executor_worktrees`.
6. Локальный `codex exec` правит код по замечаниям.
7. Сервис запускает `bash bin/ci_validate.sh`.
8. Если проверка зелёная, сервис делает коммит и отправку изменений в head-ветку PR.
9. GitHub снова запускает проверку, и цикл повторяется до готовности к слиянию.

## Важная оговорка про OAuth

Для приватного репозитория ручной вход в сервис проверки и исполнитель должен использовать:

- `GITHUB_OAUTH_SCOPE=read:user repo`

Но одного пользовательского `OAuth` недостаточно для полностью автоматического запуска после review, потому что webhook приходит без сеанса браузера пользователя. Поэтому для полного автоматического режима нужен ещё один серверный способ доступа к GitHub:

- `GITHUB_EXECUTOR_TOKEN`

или

- `GitHub App`

Дополнительно в текущей схеме уже зафиксированы три ограничения безопасности:

- GitHub OAuth-токены reviewer и executor лежат в серверном файловом хранилище сеансов, а не в client-side cookie;
- executor получает в prompt только review-сводки и inline-комментарии от разрешённых логинов проверяющего сервиса, без произвольных issue-комментариев.
- чистый `COMMENTED` review без inline-комментариев больше не запускает executor и не создаёт ложный prompt на автоматическую правку.
- при ручном повторном прогоне executor не должен повторно проигрывать старые замечания после более позднего `APPROVED` от того же проверяющего:
  - сначала берётся последнее review этого проверяющего по всем состояниям;
  - если оно уже сняло замечания, старые `CHANGES_REQUESTED` и их inline-комментарии в prompt не попадают
- executor отправляет изменения через обычный `https://github.com/<repo>.git`, а сервисный токен подаёт во временный `GIT_ASKPASS`, не помещая его в аргументы процесса `git`.
- если локальный `Codex CLI` молчит, не печатает новую строку или зависает на приёме большого prompt, reviewer и executor теперь всё равно завершают такой процесс по настроенному таймауту, поэтому зависший локальный запуск не должен навсегда блокировать повторный прогон того же `Pull Request`.

Состояние на `18 мая 2026`:

- у `origin` уже создана ветка `main`
