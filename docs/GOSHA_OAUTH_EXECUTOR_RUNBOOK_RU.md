# GOSHA OAUTH EXECUTOR RUNBOOK

Этот документ описывает локальный исполнительный сервис `Codex`, который автоматически вносит правки в ветку `Pull Request`.

## Что это за сервис

Сервис работает отдельно от проверяющего сервиса и выполняет другую роль:

- проверяющий сервис читает `Pull Request` и пишет замечания;
- executor читает замечания, делает правки в отдельной рабочей копии, запускает проверку, создаёт коммит и отправляет изменения в head-ветку PR.

## Где лежит код

- сервис:
  - `/home/max/GOSHA_PLATFORM/oauth_executor`
- локальный запуск:
  - `/home/max/GOSHA_PLATFORM/bin/run_local_oauth_executor.sh`

## Как работает цикл

1. GitHub присылает review с замечаниями.
2. Локальный `oauth_executor` принимает ручной запуск через `GitHub OAuth` или автоматический запуск по webhook.
3. Сервис создаёт отдельную рабочую копию через `git worktree` в `local_only/`.
4. Локальный `codex exec` вносит правки в этой рабочей копии.
5. Сервис запускает проверку:
   - по умолчанию `bash bin/ci_validate.sh`
6. Если проверка успешна, сервис:
   - делает коммит;
   - отправляет изменения в head-ветку PR;
   - оставляет верхнеуровневый комментарий в PR.

## Важное разделение ролей

- `oauth_reviewer`:
  - читает PR и публикует замечания
- `oauth_executor`:
  - применяет правки по замечаниям

Это сделано специально, чтобы не смешивать роль проверяющего и роль исполнителя.

## Что нужно в env

Минимум для ручного режима через браузер:

- `OAUTH_EXECUTOR_SESSION_SECRET`
- `GITHUB_OAUTH_CLIENT_ID`
- `GITHUB_OAUTH_CLIENT_SECRET`
- `GITHUB_OAUTH_REDIRECT_URI`
- `GITHUB_OAUTH_SCOPE`
- `OAUTH_EXECUTOR_ALLOWED_REPOS`
- `OAUTH_EXECUTOR_REPO_PATH`
- `OAUTH_EXECUTOR_CODEX_COMMAND`

Рекомендуемое значение:

- `GITHUB_OAUTH_SCOPE=read:user repo`

Это значение подходит и для публичного, и для приватного репозитория, а также позволяет тому же вошедшему пользователю не только читать PR, но и отправлять изменения в его head-ветку.

Для полного автоматического режима без ручного шага дополнительно нужно:

- `GITHUB_EXECUTOR_TOKEN`
- `OAUTH_EXECUTOR_GITHUB_WEBHOOK_SECRET`
- `OAUTH_EXECUTOR_REVIEWER_LOGINS`

Почему нужен `GITHUB_EXECUTOR_TOKEN`:

- один пользовательский `OAuth`-сеанс недостаточен для полностью автоматического запуска по webhook;
- webhook приходит без сеанса браузера пользователя;
- значит сервису нужен собственный серверный токен, чтобы:
  - прочитать PR;
  - сделать comment;
  - отправить изменения в ветку.

## Рекомендованный токен GitHub

Для полного автоматического режима удобнее использовать:

- fine-grained personal access token

или

- `GitHub App`

В текущей первой версии сервиса прямо поддержан путь через `GITHUB_EXECUTOR_TOKEN`.

## Локальный запуск

1. Установить зависимости:

```bash
cd /home/max/GOSHA_PLATFORM
python3 -m pip install -r oauth_executor/requirements.txt
```

2. Экспортировать env-переменные по примеру:

- `/home/max/GOSHA_PLATFORM/oauth_executor/.env.example`

3. Запустить сервис:

```bash
cd /home/max/GOSHA_PLATFORM
bash bin/run_local_oauth_executor.sh
```

4. Открыть:

```text
http://127.0.0.1:18912
```

## Проверка готовности

Быстрый `healthz`:

```bash
curl http://127.0.0.1:18912/healthz
```

Ожидаемые поля:

- `github_ready`
  - настроен ли `GitHub OAuth`
- `service_token_ready`
  - есть ли серверный `GitHub` токен для полного автомата
- `webhook_ready`
  - включён ли полный автоматический цикл по webhook
- `codex_ready`
  - виден ли локальный исполняемый файл `codex`

## Ручной режим через браузер

1. Нажать `Войти через GitHub`.
2. Указать:
   - репозиторий
   - номер `Pull Request`
3. Нажать `Запустить исполнителя`.
4. Смотреть задачу исполнения и лог.

## Автоматический режим по webhook

Текущая версия слушает:

- `POST /webhooks/github`

Условия автоматического запуска:

- событие `pull_request_review`
- действие `submitted`
- автор review входит в `OAUTH_EXECUTOR_REVIEWER_LOGINS`
- состояние review:
  - `commented`
  - или `changes_requested`

Важно:

- текущая версия поддерживает только PR из того же репозитория;
- PR из форка пока не поддерживается автоматически.

## Где лежат рабочие копии

По умолчанию:

- `/home/max/GOSHA_PLATFORM/local_only/oauth_executor_worktrees`

Сервис специально не правит основной рабочий каталог напрямую.

## Что делает локальный Codex

В рабочей копии `codex exec` получает:

- данные PR;
- review-замечания;
- верхнеуровневые комментарии;
- inline-комментарии по строкам;
- правила из `AGENTS.md`.

После работы он должен:

- изменить код;
- записать короткое сообщение коммита;
- записать краткое резюме правок;
- не делать коммит и не делать отправку изменений сам.

Коммит и отправка изменений делаются сервисом отдельно, чтобы цикл был воспроизводимее.

## Что уже делает текущая версия надёжнее

- не запускает вторую активную задачу для того же `Pull Request`, если первая ещё в очереди или уже работает;
- перед повторным прогоном очищает отдельную рабочую копию до состояния `origin/<head-ветка>`;
- убирает из следующего входа собственные служебные комментарии исполнителя, чтобы агент не спорил сам с собой;
- честно показывает в `healthz`, найден ли локальный исполняемый файл `codex`.
- не должен отправлять в git служебные файлы `.codex_executor_*`:
  - итоговое сообщение `Codex` теперь удаляется до коммита;
  - служебные файлы исполнителя дополнительно внесены в `.gitignore`

## Ограничения текущей версии

- нет автоматического merge;
- нет поддержки PR из fork-репозитория;
- нет автоматического разрешения конфликтов при параллельной отправке изменений в ту же ветку;
- если проверка `ci_validate.sh` падает, сервис останавливается и пишет ошибку в лог и в комментарий PR.
- если используется временный туннель без собственного домена, внешний адрес webhook может смениться после переподключения;
  - в таком случае нужно обновить URL webhook в GitHub под новый внешний адрес.

## Безопасность

- не логировать токены и секреты;
- держать `GITHUB_EXECUTOR_TOKEN` только во внешнем env-хранилище;
- не использовать основной рабочий каталог как место правок исполнителя;
- не давать сервису права на merge, если это не требуется отдельно.
